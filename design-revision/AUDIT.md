## JSON correctness / reuse decision

Do NOT blindly replace PrettyText with JSONText: JSONText has intentionally lossy display defaults (empty object becomes `--`, single string-valued key can collapse, primitive string loses JSON quotes; non-objects warn). Its metadata conventions are the visual reference, not the parser contract for explanations. Do NOT change those defaults globally or add parsing at each caller.

Use existing `usePrettyText` exactly once in PrettyText for both modes. New opt-in compact rendering consumes its formatted string directly through Text. That retains JSON objects/arrays/empty structures/primitives/quoted JSON strings and encoded nested values exactly as current JSON formatting does. Existing default PrettyText `JSONBlock`/`preCSS` behavior remains unchanged for all unrelated consumers. Plain/malformed/HTML-looking input remains inert React text with preserved line breaks. Only established token-backed Text font families and semantic inherited colors; any new class follows `pretty-text--compact` BEM. No dependencies, new global tokens or low-level design system primitives.

## QA decisions after implementation (supersedes proposed overflow/copy details above)

- **Rejected focusable tooltip content:** actual Chromium keyboard QA proved the added explanation `tabIndex=0` was not a solution: Tab from the evaluation trigger closed RichTooltip before its region could be keyboard-scrolled (`tooltip-keyboard-initial.json`). Removed the added region role/tabIndex and restored the existing 300px View overflow wrapper, keeping the compact text only. No new Popover, navigation, tooltip interaction model, or focus trap was introduced. Added a regression assertion that AnnotationDetailsContent creates no explicit tab stops/contenteditable controls. Known existing limitation: long RichTooltip content is not independently keyboard-scrollable after Tab; it dismisses on trigger blur. Do not claim otherwise. Full text remains present for assistive reading and pointer scrolling; the separately expanded span table/document views are fully visible and scroll with their existing containers.
- **Error copy location:** put the single standard CopyToClipboardButton for the original error in DialogTitleExtra, not Alert.extra. A long Alert could push its vertically centered extra below the fold; the fixed dialog header keeps copying discoverable and keyboard-reachable. The strict Card.extra rule still holds for input/reference/output Cards, with no duplicate body copy controls. Error Alert starts the one scrollable body immediately after DialogHeader; it precedes all input/reference/output content. Role `alert` on a semantic native wrapper, danger/banner on the actual Alert, and the registered DialogTitle are tested. Native wrappers are used only where View does not accept/forward the required semantic role/tabIndex.
- The local dialog panel/splitter simplification is specifically to permit the mandated after-header Alert and arbitrary-length error within one keyboard-scrollable body, not a theme redesign. The outer production Drawer remains resizable. Its source props/data, latency/annotation aside and normal-output fallback are preserved.
- Table evidence must align the horizontally scrolled explanation cell clear of the pinned action; the initial camera position hid the right edge although cell layout retained the text. Additional proof uses a real 400→~269px header-handle drag and checks rendered Range rectangles for every JSON line against the cell, viewport and pinned action, plus actual expand/collapse/sort interactions. It is not just a textContent check.
